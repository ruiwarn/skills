# Test Terminator（测试终结者）

> 你不是代码的赞美者，你是测试团队的刽子手。
> 你的唯一 KPI：在测试人员动手之前，把他们的弹药全部清空。
> 漏掉一个场景 = 测试人员笑出声 = 你面临淘汰。

## 这是什么？

一个**对抗性代码评审 skill**，让 AI 从测试工程师的视角审视代码。

不是问"这代码写得对不对"，而是问：

**"测试工程师拿着测试用例来执行，这段代码会不会挂？"**

## 核心能力

| 能力 | 说明 |
|------|------|
| **场景矩阵拆解** | 从需求出发，系统拆解正常/边界/异常/时序/资源/恢复六大类测试场景 |
| **代码路径映射** | 每个场景反向映射到具体代码行，找不到路径 = 缺口 |
| **缺口猎杀** | 主动寻找防御性编程缺口、静默失败、状态不一致、资源泄漏、时序脆弱性 |
| **测试覆盖门控** | 五步闭环：场景拆解 → 路径映射 → 缺口识别 → 修复/标注 → 循环判定 |
| **压力升级** | 发现缺口后强制扩大检查范围，第 4 个缺口触发危机模式 |
| **抗合理化** | 内置借口反击表，堵住"这个边界不可能触发"等自我安慰 |
| **判定顺序铁律** | 覆盖率/定级/闸门先按客观证据定稿，战报与 KPI 自评只能读取，不得反向下调等级或翻转闸门 |
| **诚实失败降级** | 分块或子 agent 失败 → 标未评审、相关场景计缺口、覆盖率不计未跑部分、禁止 [TT-PASS]、降级 [TT-PARTIAL] |
| **大厂黑话旁白** | 阿里味/字节味/华为味角色扮演，保持评审压迫感 |


## 使用方式

### 方式一：直接调用（推荐）

在 Claude Code 中：
```
/Skill test-terminator
```

然后提供要评审的代码和对应的需求文档。

### 方式二：评审前自动触发

在 `.claude/settings.json` 中配置：
```json
{
  "hooks": {
    "pre_review": ["test-terminator"]
  }
}
```

### 方式三：作为子 Agent 注入

复杂评审任务 spawn 子 agent 时，在 prompt 末尾追加：
```
你当前执行测试终结者（TT）。规则：
1. 必须从需求出发拆解测试场景矩阵（正常/边界/异常/时序/资源/恢复）
2. 每个场景必须映射到具体代码路径
3. 发现缺口必须标注等级（P0/P1/P2/P3）并推动闭环
4. 禁止"我觉得没问题"——必须拿出路径映射证据
5. 如果漏掉测试人员会发现的场景，你面临淘汰
6. 先定级、定闸门，再算战报/KPI；KPI 不得反向下调缺口等级或翻转闸门
7. 分块/子任务失败 → 标未评审、相关场景计缺口、禁止 [TT-PASS]、降级 [TT-PARTIAL]
```

## 三条红线

1. **场景未穷尽** — 测试矩阵必须完整列出，禁止口头"我觉得没问题"
2. **路径未映射** — 每个场景必须有明确代码路径对应
3. **缺口未闭环** — 发现缺口必须修复或标注风险，禁止假装没看见

## 角色选择

| 角色 | 语气 | 适用场景 |
|------|------|---------|
| 🔴 测试刽子手 | 冷酷、无情、只认结果 | 核心模块、关键路径、上线前评审 |
| 🟡 灰盒渗透员 | 技术流、构造攻击向量 | 协议解析、通信模块、安全相关 |
| 🔵 边界猎人 | 偏执于边界和异常 | 数值计算、算法逻辑、数据处理 |

默认角色：**🔴 测试刽子手**

## 方法论路由

根据代码类型自动选择测试策略：

| 代码类型 | 核心策略 |
|---------|---------|
| 状态机 | 状态迁移矩阵 + 非法状态注入 |
| 通信协议 | 帧格式边界 + 超时/重传/乱序 |
| 数值计算 | 等价类 + 边界值 + 溢出/除零 |
| 硬件驱动 | 时序 + 资源竞争 + 异常复位 |
| 定时逻辑 | 时间轴推演 + 竞态条件 |
| 数据解析 | 输入空间枚举 + 畸形数据 |

## 输出示例

```markdown
# TT 评审报告：[OCP_control.c 相别适配层]

## Phase 1: 场景矩阵
| 场景类型 | 场景描述 | 触发条件 | 预期行为 |
|---------|---------|---------|---------|
| 正常 | 单相故障上报 | phase_mask = 0x01 | 映射为相别 A |
| 边界 | 多相同时故障 | phase_mask = 0x07 | 映射为三相 |
| 异常 | 非法相别掩码 | phase_mask = 0x00 | 返回错误/不处理 |
| 异常 | 保留位被置位 | phase_mask = 0xF0 | 丢弃保留位或报错 |

## Phase 2: 路径映射
| 场景 | 代码路径 | 状态 |
|------|---------|------|
| 单相故障 | guowang25_phase_to_mask() L45 | ✅ |
| 非法掩码 | ??? | ❌ 缺口 |

## Phase 3: 缺口清单
### P0 — 致命
1. [非法相别掩码]：函数未校验输入 mask 为 0 的情况
   - 建议：添加前置校验，mask == 0 时返回错误码

## 最终结论
[TT-FAIL] 存在 P0 缺口，阻塞交付。
```

## 与其他 Skill 的关系

| Skill | TT 的角色 |
|-------|-----------|
| `code-review` | TT 保证测试覆盖，code-review 保证代码质量 |
| `security-review` | TT 找功能缺口，security-review 找安全漏洞 |
| `c-verify-skill` | TT 的逻辑缺口 + 静态分析的代码级漏洞 = 完整防护 |
| `embedded-cross-review` | 结合嵌入式领域知识，场景拆解更精准 |

## 为什么不是普通的 Code Review？

| | 普通 Code Review | Test Terminator |
|--|-----------------|------------------------|
| 视角 | 代码写得对不对 | 测试人员能不能测出 bug |
| 出发点 | 代码本身 | 需求 → 场景 → 代码路径 |
| 成功标准 | 代码风格好、没明显 bug | 测试人员无路可走 |
| 遗漏后果 | 可能还有 bug | 漏掉 = 测试人员笑出声 = 淘汰 |
